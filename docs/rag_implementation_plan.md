# RAG Implementation Plan (Latin LiLa/LEMLAT + LatinAffectus)

## TL;DR

We will build a **small, high-signal “lexicon context” block** that is computed deterministically from PostgreSQL and injected into prompts for the Latin Llama (8B) model. The block will:

1) **Lemmatize** the submitted text using the **existing scraped lookup lemmatizer** (token → lemma + coarse POS)  
2) **Join** lemmas to **LatinAffectus** (lemma → polarity; disambiguate by POS when possible)  
3) Optionally **enrich** by linking to LiLa/LEMLAT (`lila.lemmario_clean`) to obtain stable lemma IDs (`id_lemma`) + POS tags  
4) Emit a **compact, structured prompt snippet** (top-K sentiment-bearing lemmas, coverage, negation/shifters) to guide the LLM without overloading context.

This is the “Hard-to-Soft” bridge: hard facts from DB → small injection → better downstream sentiment reasoning.

## Goals

### Primary goal (sentiment RAG)

Given a Latin passage, produce a compact injection block that helps the model:

- anchor sentiment to **ground-truth lemma polarity** when available
- handle **negation/scope** better (a frequent failure mode)
- communicate **coverage/uncertainty** (don’t overclaim when lexicon coverage is low)

### Secondary goals (future-proofing)

- Make it easy to add:
  - short “micro-glosses” (definitions) per lemma
  - morphology cues (when they strongly affect sentiment)
  - caching/materialized views for performance

---

## Database Strategy (one DB, minimal friction)

We will keep a **single Postgres database** for all Latin resources and RAG computation (simplifies joins, caching, and deployment).

### Current schema layout (recommended for now)

We will keep **two schemas** and build the initial RAG logic purely in code:

- `public.*` = scraped lookup lemmatizer tables (`public.lemmas`, `public.forms`)
- `lila.*` = LiLa/LEMLAT + LatinAffectus (`lila.lemmario`, `lila.analysis`, `lila.sentiment`, plus `*_clean` views)

Do we need a dedicated `rag.*` schema right now?

- **No** — not necessary to start, because we can compute the priors on the fly from `public.*` + `lila.*`.
- **Later**, if we need performance/caching, we can add `rag.*` for derived tables/materialized views (e.g., cached lemma→sentiment joins), without changing the core join keys.

## Canonical Join Key (the critical piece)

We need a robust key to join across:

- LEMLAT lemma strings (may be padded/escaped; already trimmed in `lila.lemmario_clean`)
- LatinAffectus lemma strings (plain text)
- Scraped lemma strings (often with diacritics)

### Proposed key

**`lemma_key`**: normalized lemma string:

- lowercase
- diacritics removed
- punctuation collapsed/removed

Implementation can mirror the existing `norm()` function pattern used in the scraper DB (`unaccent(lower(t))`), plus trimming and character filtering as needed.

### POS handling

LatinAffectus includes `pos` (e.g. `adj`, `noun`, …). We should:

- prefer scraped POS (`public.lemmas.pos`) as the first disambiguator, because our runtime lemmatization step is based on scraped lookup
- map scraped POS values into the LatinAffectus buckets (e.g. `noun|adj|verb|adv|other`)
- join on `(lemma_key, pos_bucket)` when possible; fall back to lemma-only join when POS is missing/ambiguous
- optionally cross-check LiLa POS (`lila.lemmario_clean.upostag`) when linking to `id_lemma`

This reduces homograph errors (same surface lemma with different POS/senses).

## RAG: “Hard-to-Soft” Pipeline (runtime)

### Step 0 — Preprocess

Input: user-submitted Latin text

- Unicode normalize
- tokenize to word tokens
- normalize tokens for lookup (lowercase + strip punctuation/quotes; keep the original token for reporting)
- drop “irrelevant” tokens:
  - punctuation-only tokens
  - numeric-only tokens
  - optional stopwords list (small and configurable; keep negators like `non` even if stopworded)

Output: token list (with counts)

### Step 1 — Lemmatize via the scraped lookup DB (existing lemmatizer)

Purpose: deterministically map tokens → lemmas using data we already have and trust.

Data needed:

- `public.forms` (surface form → lemma_id)
- `public.lemmas` (lemma_id → lemma string + scraped POS)

Output per token:

- token
- `lemma_nod` (normalized lemma string; our join key)
- `pos` (coarse POS from scraper, when present)
- lookup status: `hit|miss`

Policy decision:

- keep top-1 lemma per token (lookup returns one lemma_id); track coverage stats (how many tokens miss)

### Step 2 — Join to LatinAffectus

Purpose: attach polarity to lemmas.

Data needed:

- `lila.sentiment` (lemma + pos → polarity_score + label/provenance)

Output per lemma:

- lemma
- pos
- polarity_score
- has_polarity
- provenance
- count in text
- join_confidence (pos-match vs lemma-only match)

### Step 2.5 (optional) — Link to LiLa/LEMLAT lemma IDs for stability

Purpose: attach stable internal IDs (`id_lemma`) and LiLa POS tags, without changing the core sentiment join.

Data needed:

- `lila.lemmario_clean` (trimmed lemma inventory with `id_lemma`, `lemma_reduced`, `upostag`)

Output (per lemma):

- `id_lemma` candidates (0..N; N>1 possible due to homographs)
- LiLa POS tags (`upostag`, `upostag_2`) when present

This is mainly for: caching, debug visibility, future joins (and later, future LiLa-native lemmatization if desired).

### Step 3 — Select “what to inject” (top-K)

We must keep injection small. For sentiment analysis, the best single heuristic is:

**`importance = abs(polarity_score) * count`**

Inject only the top K lemmas with sentiment hits, plus a small set of “context cues”.

Recommended defaults:

- `K = 15–25` (tune by average text length and desired prompt budget)
- ignore lemmas with `abs(score) < threshold` (optional)

### Step 4 — Add valence shifters (negation/intensifiers)

The model will miss scope unless we nudge it.

Extract from token list:

- negators: `non`, `haud`, `nec/neque`, `nemo`, `nullus`, `sine`, `vix`, `ne`, …
- intensifiers/attenuators: `valde`, `nimis`, `tam`, `satis`, `parum`, `paene`, …

Inject counts only (tiny).

### Step 5 — Emit compact injection block

Format should be easy to parse for the LLM and stable for debugging.

Suggested format (YAML-ish or JSON-ish; choose one and keep it consistent):

```
LEXICON_PRIORS:
  coverage:
    tokens: <n>
    lemmatized_tokens: <n>
    affectus_hits: <n>
    affectus_hit_rate: <0..1>
    ambiguous_tokens: <n>
  negators: { non: 3, nec: 1, sine: 1 }
  shifters: { valde: 1, vix: 1 }
  hits: [
    { lemma: "ferox", pos: "adj", score: 0.5, label: "positive", count: 2, source: "LatinAffectus", pos_match: true },
    ...
  ]
RULES:
  - "Use hit scores as priors; do not invent lemma polarity not supported by hits."
  - "Apply negation/shifters: negation flips/dampens; intensifiers amplify."
  - "If hit_rate is low, explicitly report uncertainty."
```

This is usually a few hundred tokens even at K≈20.

## Where scraped tables fit (and what they do NOT provide)

The current scraped pipeline (tables `lemmas`/`forms`) is best for:

- explicit morphology columns per inflected form (mood/tense/voice/person/number/case/…)
- provenance URL (`page_url`)

It **does not** currently store English definitions/glosses. If we want definitions for RAG, we must add a definitions source:

- extend scraper to extract and store definitions, or
- import another offline dictionary dataset, or
- resurrect/import legacy definition data (if acceptable), or
- accept online lookups (not recommended for “hard facts” RAG).

For *sentiment* RAG specifically, definitions are optional; if added, prefer **micro-glosses** (5–10 words) only for top-K injected lemmas.

## Minimal DB contract (tables + columns we will use)

This is the “stable interface” the RAG code should rely on.

### Scraped lookup lemmatizer (runtime backbone)

- `public.forms`
  - `form_nod` (normalized surface form; token lookup key)
  - `lemma_id` (FK to the lemma row)
- `public.lemmas`
  - `id` (PK; joins from `public.forms.lemma_id`)
  - `lemma_nod` (normalized lemma string; primary join key across datasets)
  - `pos` (scraped POS; used to disambiguate sentiment when possible)
  - `lemma_diac` (display-only; optional debug)

### Sentiment lexicon (RAG payload)

- `lila.sentiment`
  - `lemma` (string key; normalize at query time with `norm(...)`)
  - `pos` (optional; use when it matches)
  - `polarity_score` (numeric prior)
  - `has_polarity` (label fallback)
  - `provenance` (debug/audit)

### Optional “stable ID” enrichment (not required for sentiment join)

- `lila.lemmario_clean` (view)
  - `id_lemma` (stable lemma ID)
  - `lemma_reduced` (join target; normalize at query time with `norm(...)`)
  - `upostag`, `upostag_2` (POS-ish tags; secondary disambiguation / future use)

## Phase 2 architecture (testing-first, no LLM yet)

We will implement a single passage-level component that:

1) tokenizes and normalizes a Latin passage
2) looks up lemmas via the existing scraped lookup DB (`public.*`)
3) joins lemma keys to LatinAffectus sentiment (`lila.sentiment`) using lemma_key + POS buckets
4) optionally links lemma keys to stable LiLa lemma IDs (`lila.lemmario_clean.id_lemma`)
5) returns a compact, deterministic result that we can inspect in the terminal before touching the LLM

### Code structure (where this lives)

Keep Phase 2 work under `src/Lemmatizer-LTN-LiLa/`:

- module: `src/Lemmatizer-LTN-LiLa/rag/latin_lexicon_annotator.py`
  - class: `LatinLexiconAnnotator`
  - primary method: `annotate(text: str) -> dict` (JSON-serializable)
  - uses a persistent DB connection + optional in-memory caches (token→lemma, lemma→sentiment)
- debug runner: `scripts/latin_lexicon_annotator_debug.py`
  - read Latin text from stdin/arg, print coverage + top-K sentiment hits + ambiguity reports

### Why a class (vs a function)

For long passages, we want:

- one persistent DB connection (avoid reconnecting / per-token overhead)
- batched queries (lookup many tokens/lemmas at once)
- optional caching for repeated runs (e.g., in a notebook or during evaluation)

So the clean API is a class with `annotate(...)`. We can still expose a small convenience function later.

### Tokenization & normalization (deterministic)

We are not depending on CLTK here yet. The annotator should implement a simple tokenizer:

- Unicode normalize (NFC)
- split into word tokens (letters only; keep `u/v` and `i/j` as-is for now)
- lowercase, strip punctuation/quotes
- drop irrelevant tokens:
  - punctuation-only / empty tokens
  - numeric-only tokens
  - optional small stopword list (configurable)
  - never drop negators/shifters (e.g., `non`, `nec`, `haud`) even if stopworded

This is sufficient for Phase 2 correctness tests and keeps behavior stable.

### DB query strategy (batch-first)

1) **Token → scraped lemma_key**

- normalize tokens for DB lookup using `public.norm(token)`
- query `public.forms` for all tokens in one call (conceptually):
  - `SELECT f.form_nod, f.lemma_id FROM public.forms f WHERE f.form_nod = ANY(%s)`
- then join lemma metadata:
  - `SELECT l.id, l.lemma_nod, l.pos FROM public.lemmas l WHERE l.id = ANY(%s)`

2) **lemma_key → sentiment (POS-disambiguated)**

Join `public.lemmas.lemma_nod` to `norm(lila.sentiment.lemma)`:

- primary: lemma_key + POS bucket match (scraped POS → bucket; affectus POS → bucket)
- fallback: lemma_key only (record that we fell back)

3) **(Optional) lemma_key → LiLa stable IDs**

Link `public.lemmas.lemma_nod` to `norm(lila.lemmario_clean.lemma_reduced)` (fallback to `lemma`), and keep 0..N candidates:

- if multiple `id_lemma` candidates exist, include them all and report ambiguity
- use POS (`public.lemmas.pos` vs `lila.lemmario_clean.upostag`) as a tie-breaker when possible

### Output contract (what we print/test)

`LatinLexiconAnnotator.annotate(text)` should return a dict with:

- `coverage`: token_count, lookup_hits, lookup_misses, affectus_hits, affectus_hit_rate, fallback_rate, ambiguous_lemma_ids
- `negators` / `shifters`: counts by token
- `lemmas`: per-lemma aggregates (lemma_key, count, scraped_pos_bucket)
- `sentiment_hits`: per-lemma sentiment (score/label, pos_match flag, provenance, count, importance)
- `top_k`: top-K list for inspection (ranked by `abs(score) * count`)

This gives us a deterministic “ground truth features” layer we can validate before adding any prompt injection.

## Answer: “Do we need to clean up and consolidate into one DB and rename/rework everything?”

**Consolidating into one DB is correct** for the RAG goal (fast joins, simpler deployment).  
**Renaming/reworking is helpful but not strictly required** to begin RAG:

- You can start immediately with the current tables/views and build the injection block from them.
- Once the pipeline works end-to-end, do the cleanup (schemas/prefixes, stable interface objects) to reduce confusion and operational risk.
